# 服务时间价值算法与验证契约 V0.1

日期：2026-11-01。状态：候选定义及隔离验证实现；尚未替换工程与比赛现行算法。数据范围：synthetic / fixture；模型标记：candidate。本文补充时间价值，不改变0.1.1的Rs/Hs、现有T01三类时间、D02窗口终点覆盖和D04固定效用语义。

## 1. 本次要解决的问题

终点都恢复，不表示中间承受的损失相同。只记录首次恢复，又会漏掉恢复后的再次中断。因此需同时输出逐时段服务满足程度、累计缺口和相对基线的备用增益。首版采用恒定需水、分段恒定供给、显式分配，不推断尚未提供的配送量、库存、任务工期或水质。

总体业务服务满足原则是：**使用方指定的全部必要条件均有证据且满足**。条件可包含供水量、压力、连续性、水质和接入方式；任一必要条件已知不满足，判不满足；没有已知失败但仍缺必要证据，判未知。不同供水渠道不能机械共用一个压力门槛，例如送水到储水设施需要接收能力及水质证据。

本轮可执行子集仅为`quantity_only_independent_delivery`：管网与备用的流量均指到达服务对象的独立、可相加的供给，水量满足程度可计算；**不据此输出“饮用水达标”或完整医院服务已满足**。接入网络并改变水力的备用水源须重新求解整个网络，不能再把源端出水直接叠加到节点水量。

## 2. 数学定义、单位与依据

### 2.1 水量满足程度

对目标服务记录i、时间片k（左闭右开，长度Δt，单位h）：恒定需求为Dᵢ（m³/h）；Qᵢᵏ为已声明且有证据的主网终端供给；xᵢₛᵏ为独立备用源s分配到该目标的终端供给。要求Dᵢ>0时：

\[
r_i^k=\min\left(1,\frac{Q_i^k+\sum_s x_{is}^k}{D_i}\right),\qquad
b_i^k=\mathbf1[r_i^k\ge\rho_i],\quad0<\rho_i\le1.
\]

ρᵢ是经确认的本次水量满足阈值，不等于概率；fixture取1。Dᵢ=0时比例为null、状态no_demand、本时间片损失为0。它不意味着“该服务已通过业务验收”。超出需求的供给不产生额外收益，但仍消耗分配源库存。

供给/需求比可参考[WNTR水力韧性指标](https://usepa.github.io/WNTR/resilience.html)中水服务可用性的思想；本合同的截断、目标集合、分片积分、零需水及未知状态是**我方候选设计**，不能写成论文原样公式或行业标准。

### 2.2 四个互不替代的累计指标

\[
T_{zero,i}=\sum_k\mathbf1[r_i^k=0]\Delta t_k,
\quad T_{unmet,i}=\sum_k\mathbf1[r_i^k<\rho_i]\Delta t_k,
\]
\[
L_{eq,i}=\sum_k(1-r_i^k)\Delta t_k,
\quad V_{miss,i}=\sum_kD_i(1-r_i^k)\Delta t_k.
\]

| 输出键 | 含义/单服务单位 | 不能表述为 |
|---|---|---|
| `complete_outage_hours` | 完全无供给时长，h | 所有不达标时间 |
| `requirement_unmet_hours` | 水量未满足阈值的累计时长，h | 完全停水时长 |
| `equivalent_shortfall_hours` | 按供给缺口比例折算的服务小时，h | 真实停水小时、概率或经济损失 |
| `unserved_volume_m3` | 本窗口累计未满足水量，m³ | 管道漏失量 |

例如连续2h只供一半需求：完全停供0h；ρ=1时未满足2h；折算缺口1h。再次中断在后续片段继续累计，不以“曾经恢复”免除后续损失。

代码对小时指标统一标`service*h`以便汇总；单目标数值等于h。多个目标相加后表示记录·小时，**不能把一个医院记录与100户居民记录当成等价民生损失，也不能把重复服务范围再计一次**。当前函数不乘人口、脆弱性或CUV偏好权重；分服务明细是后续业务聚合的依据。

### 2.3 备用实际增益的定义

对于同一外部条件、同一主网恢复过程的基线p₀与备用方案p₁，针对上述任一损失指标M：

\[
\Delta M=M(p_0)-M(p_1).
\]

正数表示减少损失，0表示本窗口没有减少该项损失，负数保留，表示相对基线更差。本轮“实际增益”是**给定已声明分配后的模型增益**，不是现场实测效果，也不是备用名义容量乘时长。主网修复后再送水可以消耗库存，但不再减少已为0的当前缺水；其冗余保障价值需另外定义事件依据。

`compare_backup_gain`只允许改变备用分配及启停安排。快照、评价时钟、故障、隔离、目标与需水、需求版本、时间窗、服务判据、源容量/库存/资源及物理可用时段、主网水量过程必须一致。时间网格可不同，但合并相邻相同主网状态后必须等价。**源物理可用时间是共同外部条件，计划启动时间在allocations里**。抢修时刻变化属于更广义方案比较，此函数拒绝，不能冒充纯备用边际效应。

### 2.4 未知区间与约束

已知管网水量提供下界；缺主网信息时，其可能供给上界取需求。备用交付不确定时，下界不计入该备用，上界不超过声明的分配流量。经截断获得r⁻≤r≤r⁺：

\[
L_{eq,i}\in[\sum_k(1-r_i^{k,+})\Delta t_k,\ \sum_k(1-r_i^{k,-})\Delta t_k].
\]

其余指标按同样单调关系给界；不是概率置信区间，界也不保证联合可达到。增益保守区间为`[baseline.lower−candidate.upper, baseline.upper−candidate.lower]`；不假定两方案未知量独立，区间可能宽。上下界不等时`value=null`，不以中点、零或上界假装确定结果。

显式供给安排必须满足：每时间片同源总分配≤源容量；累计分配体积≤可用库存；供给区间落在源可用区间内；接入已知不可用则不可行。资源约束为：

\[
\sum_{s:\sum_i x_{is}^k>0}a_{sr}\le B_r.
\]

同一个源服务多个目标，固定资源需求只计一次，供水量按所有目标相加。首版仅检查**正流量供给时间片内的共享资源占用**，未含赶路、连接、撤收、补水、抢修任务及切换耗时；这些阶段需要独立reservation数据。容量不足但明确分配较少是部分服务，可计算；声明的分配超容量才是infeasible。缺容量、库存、共享资源数或接入确认，则约束unknown，不自动宣称可行。算法不替用户重分配或自动在库存耗尽时截断。

EPS=1e-9仅是数值比较容差，不是业务允许偏差。所有输入及派生积分须有限；时间片重叠、倒置、超窗均拒绝。窗口[0,H)，H时刻开始的事件面积为0；首次恢复等端点指标仍由相应时间函数单独处理。

## 3. 函数TV01：evaluate_service_time_value

**用途/版本**：计算给定水量过程的4个损失指标及上下界。版本`service-time-value-0.1`。签名`evaluate_service_time_value(request: dict) -> dict`。纯函数，不改输入对象、不写数据库、不触发调度。

| 输入字段 | 类型/单位/例子 | 用途与提供方 |
|---|---|---|
| `data_mode` | enum，`synthetic` | 本候选只接合成；我们标记 |
| `criterion` | enum，`quantity_only_independent_delivery` | 显式量化判据；我们定义、业务后续确认 |
| `plan_id` | nonempty string，`fixture-backup` | 方案标识，我们生成 |
| `context.snapshot_id` | string，`fixture:s01-time-value:20261101` | 运行快照，我们适配上游 |
| `context.as_of` | ISO8601带时区，如`2026-11-01T00:00:00+08:00` | 共同评价时钟，数据/业务方确认 |
| `context.fault_id/isolation_id/demand_version` | string，各自版本化ID | 防跨情景/隔离/需求比较，我们登记 |
| `horizon_hours` | finite number>0，h，8 | 积分窗口，任务提出方 |
| `services` | ID→object映射 | 固定服务对象；权属方提供实际映射，我们构造fixture |
| `services[id].demand_m3h` | finite number≥0，m³/h，4 | 恒定需求，本轮假设；真实业务由权属/服务对象提供 |
| `services[id].required_ratio` | finite number，(0,1]，1 | 水量最低满足比例，业务方确认，非模型自由生成 |
| `sources[id].capacity_m3h` | number≥0或null，m³/h，5 | 送达上限；运维/供应方 |
| `sources[id].volume_m3` | number≥0或null，m³，100（fixture） | 窗口可用库存；运维/供应方；不默认无限 |
| `sources[id].independent_of_network` | bool，true | 独立终端供给假设；水力耦合水源不适用加法 |
| `sources[id].available_from_h/to_h` | number≥0，h，0/8，后者大于前者 | 外部可用窗口，供应方 |
| `sources[id].resources` | resource ID→number>0，`{"water_truck":1}` | 每源供给时固定资源需求，运维方 |
| `sources[id].evidence_ref` | string或null | 容量/库存说明引用；缺证据降低结果确定性 |
| `resource_capacities` | resource ID→number≥0或null，`{"water_truck":1}` | 共享资源能力，运维方；数量单位按ID定义保持一致 |
| `segments` | object[]，例[0,1)、[1,6)、[6,8) | 事件间的恒定片段，我们从明确事件/流量生成 |
| `segments[].start_h/end_h` | number≥0，h，1/6 | 相对as_of偏移，end≤H |
| `segments[].network_m3h` | service ID→number≥0或null | 终端主网供给；合成假设或水力/监测结果，非图可达布尔值 |
| `segments[].evidence_ref` | string或null | 该片段主网流量来源 |
| `segments[].allocations[]` | object：`source_id,service_id,flow_m3h,connection_ready,evidence_ref` | 显式备用分配；flow单位m³/h，connection为bool/null |

示例调用（完整8个请求保存在实验results.json）：

```python

r = request(demand=4, backup_start=1, backup_end=6, backup_flow=4)
out = evaluate_service_time_value(r)
# out['metrics']['unserved_volume_m3']:
# {'status':'succeeded','value':4.0,'lower':4.0,'upper':4.0,'unit':'m3'}
```

输出合同：

| 输出 | 类型/示例 | 含义 |
|---|---|---|
| `status` | enum，succeeded/partial/insufficient_data/infeasible/invalid_input/unsupported/not_applicable | 计算状态，succeeded不等于方案服务充分或获业务批准 |
| `constraint_status` | pass/unknown/fail/not_applicable | 仅本合同覆盖的约束；不代表完整调度已检查 |
| `metrics[key]` | `{status,value,lower,upper,unit}`，value number/null | 四种累计指标；未知保持null与界 |
| `per_service[id].timeline` | `{start_h,end_h,ratio_lower,ratio_upper,state}[]` | state为meets_quantity/quantity_shortfall/insufficient_data/no_demand |
| `per_service[id].metrics` | 与汇总同结构 | 保留不同对象贡献 |

| `qualified_water_service` | `unsupported` | 本函数不评完整供水质量 |
| `issues/violations/reason` | string[]或string，按分支返回 | 缺项、约束冲突、错误原因；失败分支没有成功指标 |
| `contract_version/request_fingerprint` | string，版本/sha256 | 同次计算留痕，不作业务签名或真实数据认证 |

结构非法/非有限量/重叠片段返回invalid_input；现实数据或其他判据返回unsupported；空目标not_applicable；不覆盖的时间段按未知补齐。已知超资源/库存/接入失败返回infeasible且不计增益。字段未证实可计算时返回insufficient_data；部分指标确定时可以partial。需求完全满足但某条多余备用接入仍未知，也不得显示全部约束通过。

## 4. 函数TV02：compare_backup_gain

**用途/版本**：`compare_backup_gain(baseline: dict, candidate: dict) -> dict`，同TV01版本。两侧请求字段完全采用TV01；基准要求见2.3。先分别计算，再逐指标相减；不根据方案名称猜测优劣。

```python
from src.algorithm_validation.run_time_value import request
from src.algorithm_validation.service_time_value import compare_backup_gain
out = compare_backup_gain(request(), request(backup_start=1))
# out['gains']['equivalent_shortfall_hours']['value'] == 5.0
# out['gains']['unserved_volume_m3']['value'] == 20.0
```

成功输出`contract_version,comparison_basis,baseline_fingerprint,candidate_fingerprint,baseline,candidate,gains,status`。gains与metrics相同结构，允许负值；同基准指纹一致不要求两方案请求指纹相同。某侧失败则保留两侧输出、gains空；共同条件不符返回`invalid_input/incompatible_counterfactual`；信息不足返回insufficient_data及保守增益界，不进入确定性效用排序。

## 6. 水力基准合同与本次测试

`hydraulic_baseline.run_case(case_id, mode, demand_model, inp_output=None)`在独立五节点fixture上运行原生EPANET2.2。mode为normal/backup/fault；demand_model为PDD/DD。输入为从既有CSV网络导出的normal_pda.inp；按mode切换管状态，输出各节点压力水头m、流量m³/s及m³/h、求解警告、质量平衡和明确的业务未验证状态。该函数是可重复实验入口，不是任意业务网络的水力API。基础INP原地不覆盖，另三份为派生输出，旧来源哈希保留；无需部署旧cuv_reference包。

正常PDA、备用PDA、断开PDA、备用DDA四工况已实际运行。压力驱动需水采用EPANET的分段关系；测试的最低/充分压力0/20m与指数0.5均为fixture。水力依据为[EPANET2.2算法说明](https://usepa.github.io/EPANET2.2/12_analysis_algorithms.html)与[WNTR水力说明](https://usepa.github.io/WNTR/hydraulics.html)，详细配置和误差见实验README。负压DDA结果仅作诊断，不当作实际可供水量。质量平衡通过也不能替代水质或业务模型校准。

## 7. 接入真实业务前待补的最小条件

1. 服务范围及去重、每服务需求曲线、最低满足比例；供应对象与运行节点明确映射。首版需水恒定，时变需水要扩展合同。
2. 每时间片实际/模型供水量、压力、质量与来源版本。水质至少需业务用途所要求的指标、实测/预测值、单位、检测时点、适用阈值与有效期；本轮不自行指定医院法定阈值。
3. 备用接收路径、真实送达能力、可用库存、补水安排和实际启停；源端能力不能替代末端送达量。
4. 班组/车辆/设备完整占用时间、赶路和连接撤收、互斥依赖及作业窗口；当前流量区间资源检查不能作为完整排程验收。
5. 可标定水力模型：高程、管径、长度、粗糙度、泵阀控制、水源边界、需水模式，以及压力/流量实测验证集。
6. 明确的业务目标、硬规则、可行方案比较案例和真实偏好标签，详见[GNN与业务标定准备](GNN漏损复现与业务标定准备_v0.1.md)。在这些标签缺失时，业务权重标定状态为insufficient_data。
